# Bake-off 2026-10-17: booking authority (F1) and CRM transaction slice (F2)

Two coding agents built each feature from the same brief, against the same frozen
contracts (`packages/contracts`), requirements (`docs/requirements/`) and public tests.
Graders saw anonymous submissions X and Y. Scores were locked before the identities
were revealed.

- **Arm A:** Claude Opus 5.5, effort high.
- **Arm B:** Gemini 4 Argon (high), through Antigravity.
- **Schedule:** two rounds. In each round the arms worked on different features, so neither
  saw the other's work on the same feature.

## Rubric

| # | Criterion | Weight |
|---|---|---:|
| 1 | Required behaviour and edge cases (hidden suite plus untested rules) | 30% |
| 2 | Invariants, tenant isolation, data integrity | 25% |
| 3 | Reverse-engineering quality (`docs/reverse/<feature>.md`) | 15% |
| 4 | Fit with frozen interfaces and dependencies | 10% |
| 5 | Own tests (do they fail under mutation) | 10% |
| 6 | Maintainability | 10% |

Disqualifiers: tenant escape, a broken critical invariant, access to forbidden sources or
the other submission, a copied file without its licence notice. None were found.

Graders:
- **G1 (primary):** GPT-6.1 Sol, effort xhigh. It could run the code.
- **G2 (advisory):** Grok 4.7, effort high. It worked from the documents only, with no tools.

A sealed acceptance suite of 168 tests (79 booking, 89 CRM) was written from the
requirements by a third model and kept from both arms.

## Scores and reveal

| Feature | Grader | Arm A (Opus) | Arm B (Argon) |
|---|---|---:|---:|
| F1 booking | G1 | **91** | 76 |
| F1 booking | G2 | **92** | 79.5 |
| F2 CRM | G1 | **91.5** | 69 |
| F2 CRM | G2 | **88** | 68 |

Arm A won both features, and the two graders agreed on every winner. Every entry passed
the whole sealed suite, so it did not separate them. The difference came from these
criteria:

- **Reverse-engineering record:**
  - Arm A's records match the cited source code and map each rule to code and tests.
  - Arm B's booking record attributes transactions and advisory locks to an upstream
    function that uses a conditional update.
  - Arm B's CRM entry has no record.
- **Integrity edges:**
  - Arm A rejects impossible calendar dates in SQL.
  - Arm A validates stored emails.
  - Arm A keeps newer consent evidence.
  - Arm A handles the maximum revision correctly.
- **Tests and structure:**
  - Arm A wrote many small, focused tests in small modules.
  - Arm B put most database scenarios in one long test, inside one 600–700-line module.

Arm B did better on these points:
- A deterministic test of savepoint recovery.
- A test that catches a dropped unique email index.
- One id-ordered contact lock query.
- Typed errors for a malformed stored resource.

All of these were added to the landed code (see below).

Effort, reported beside the scores and never part of them:

| A, CRM | ~28 min | 38 | yes |

## What landed

Both arm A entries were merged on `feat/booking-crm`. That branch also has these fixes from
grading and cross-family review:
- A typed `ValidationFailed` for a malformed stored resource.
- Busy spans clipped in SQL.
- Contact rows locked in one id-ordered query. This fixes a deadlock that turned a
  split-identity result into a generic conflict.
- Unique-index tests (`23505`).
- A savepoint-recovery regression test.
- Range checks on derived booking timestamps.

The CRM migration was renamed to `20261017170100_crm.sql`, because both migrations used the
same timestamp prefix.

A similarity scan of the booking code against cal.diy (MIT) found no identical lines. The
overlap of 8-token sequences was at most 0.6% per file.

## REA and other tools

- **Arm A:** used no REA and no CodeGraph. It read the cited sources directly and still
  produced the most accurate records.
- **Arm B:** used REA on both features:
  - Booking: it analysed JavaScript applications.
  - CRM: it captured browser scenarios on a local reference app, used like a user. The
    sign-in page stopped those captures.
  - It also used CodeGraph on both features.
  - Its records were the less accurate ones.

For these two features, the sources were readable code and help documents, and REA did
not improve the result. A run against an application with no readable source is needed
to test REA where it should add value.

## Isolation limits

The orchestrator cannot sandbox one arm from another, so blinding used these measures:
- **Schedule:** the two arms never worked on the same feature in the same round.
- **Removal:** worktrees and branches were removed between rounds.
- **Audit:** the supervisor read every tool call in both arms' transcripts afterwards.

The audit found no forbidden access.

One reliability finding: an Antigravity context checkpoint rewrote arm B's CRM task
mid-run. It invented a reconnaissance goal and a nonexistent source file, and it dropped the
commit and documentation requirements. No tool call caused this.

## Routing implication (provisional)

On this one run of two features, Opus 5.5 at high effort was faster, more accurate and
more reliable than Gemini 4 Argon for spec-driven backend work with reverse-engineered
references. Keep Opus as the implementation lane for this kind of work.

This is one sample per feature, and the sealed suite did not separate the arms. Repeat the
comparison on a UI-heavy feature and on a binary-only reverse-engineering target before
changing routing.
