The architecture

How the modules sit on the Hub, how they work together without calling each other, and how outside software is kept behind a port. From decision 0002, D1 to D9.

01

In one paragraph

There is one Hub. It holds the records, the typed events, the one approval queue and the results, and it is the only agent runtime (D5). A module is one sellable capability with one outcome the owner can read on a phone; modules never call each other and coordinate only through Hub records, events and proposed actions (D3). Outside software sits behind a port: it runs unmodified and pinned, the owner never signs in to it, and it sends nothing until the Hub re-checks the approval (D4).

Two catalogs

Software

Module catalog

One sellable software capability with one outcome. It has runtime state per tenant, actions, an approval policy and metrics. A module is only real when its actions, approval policy and metrics exist in the Hub.

Hours

Agency-service catalog

A line item with hours, a price and a deliverable (lead-leak-check, ops-audit, website-sprint, studio, set-up). It has no runtime state and never appears in a tenant's module list.

A package is a priced list of modules plus a template: { id, name, modules[], template, price, hours, headlineMetric }. It adds no behaviour. It sets module defaults for a trade, one price and one operator-hours budget. Every module in a package stays usable alone (D2). A proposal is a list of module grants plus agency-service lines with one price.

Six rules

  1. 1

    Access = at least one live grant

    (starts_at <= now < ends_at, or no end). The dispatcher checks it before any module action.

  2. 2

    Cancel

    ends that grant only. The module keeps running if another grant is live.

  3. 3

    Failed payment

    blocks grants of source addon and package after the plan's grace period; comp and proposal grants with a paid invoice stay.

  4. 4

    Comp expiry

    is an ends_at; the owner gets a notice 7 days before.

  5. 5

    Buying a module the tenant already holds

    adds no second charge: checkout shows "already included by <source>".

  6. 6

    State survives grants.

    A module that loses its last grant moves to off and keeps its config for 90 days.

05

How modules coordinate

Modules never call each other; they may need the same record. They coordinate through three shared things only (D3).

1

Hub records

Under row-level security: contact, thread, booking, deal, asset, brand profile.

2

Typed events

Written by the dispatcher's outbox (call.missed, booking.completed, review.requested). A module declares what it consumes and emits.

3

Proposed actions

Through the one dispatcher. Every outside effect (send, publish, charge, call) is an action with an idempotency key, an approval policy and an audit entry.

In practice

  • Independent does not mean no prerequisites. A module may require a shared record or a connection. Text-back needs a link to send; the booking page is the usual one and any URL the owner sets also works. requires states it and the set-up checklist enforces it.
  • Delayed work uses the Hub's templated runner, not a new workflow engine. The runner re-checks consent, STOP, cancellation and no-show at send time, not at schedule time.
  • Standing approvals expire inside 30 days. The owner gets a renewal alert 7 days and 1 day before; an expired template stops sending and shows as "needs renewal" on the module, never as silent failure.
  • One winning consumer per event. With receptionist on, it takes call.missed and textback stands down. Each consumer keeps a cursor so a replayed event does nothing twice.
  • Revisit a workflow engine when three flows need more than three durable steps with waits over a day EvidenceR4 section 1.9.

The Front Desk chain

One missed call, through to one review request. Each step is a separate module or Hub check; a stop branch ends the chain for that customer.

06

Results

Results are evidence rows, summed (D9). Every module proves its outcome the same way.

module_outcomes
  • id
  • tenant_id
  • module_id
  • metric
  • subject_type
  • subject_id
  • source_event_id
  • occurred_at
  • reversed_at
  • definition_version

unique (tenant_id, metric, subject_type, subject_id)

One row per real thing: one booking, one sent text, one review request.

  • Attributed once. A booking counts for one module, by a written rule (the last module message the customer received in the 7 days before booking).
  • Reversible. A cancelled or no-show booking sets reversed_at and leaves the sum.
  • Versioned. A changed definition gets a new definition_version; old rows keep theirs.
  • Honest names. The card says "bookings after a text", not "recovered revenue". Money appears only as the owner's own value per customer times a count, labelled as an estimate.

In the pilot the operator assembles the weekly count by hand from Hub Home data, using the same definitions. The attribution rule is a first guess: check it against the first 60 days of pilot data.

07

Ports and the one-wrapped-server rule

Each outside capability gets a typed port in the Hub with a TypeScript fake for tests and demos (D4).

  • The wrapped service runs unmodified and pinned.
  • The owner never signs in to it.
  • It never sends anything unless the Hub re-checks the approval first.
  • Its tenant mapping lives in the Hub.
  • A second-tenant denial test ships with the port.

At most one new wrapped server in year one, and it is OpenSEO, added when two clients pay for Local Visibility EvidenceR2 section D risks, checked 2026-11-11. Voice (Pipecat) is year two unless Devin swaps the order. Chatwoot waits for a paying client who needs WhatsApp or Instagram. WhisperX and Docling are not in the year-one plan.

08

Phone approach

The existing web app plus web push first; a native companion later, on a trigger (D7). The dashboard is already phone-first and installable. Phase 1 adds the approvals list, the deep link and an email alert. Phase 2 adds web push.

The tradeoff

No app-store work and one codebase, against three iPhone limits: the owner must add the app to the Home Screen before push works; the permission prompt needs a tap inside the installed app; iOS shows no action buttons on a web push, so an approval is tap, look, tap EvidenceR4 Part 2, checked 2026-11-11.

What makes it workable

  • Every alert has a fallback. An owner without push gets the email with a signed link, and a text link when they choose it. Push is an upgrade, not a requirement.
  • Returning is one step: magic link or passkey, and the deep link opens the approval itself.
  • An install card in the dashboard walks an iPhone owner through Add to Home Screen.
  • Aged approvals escalate: a second alert, then the named fallback person.
  • One receipt before any claim: an approval made from a locked iPhone on a pilot tenant.

Three measures

  1. 1Alert delivered
  2. 2Tap to recorded decision
  3. 3Time until the owner acts

Kept apart. A slow owner is not a slow product.

The native trigger

Build an Expo companion only when a product trigger fires: push opt-in under 40% after 30 days among owners who were shown the install card; delivery failures above 5%; three sales calls a month asking for a store app; or a need to share files into the app. Slow human response is not a trigger. No Capacitor wrapper (App Store rule 4.2 risk).

10

The demo against the real product

The demo shows the product vision on sample data. It is a separate small app in demo/ that talks to a HubPort interface; the default adapter is in-memory sample data shaped like the Hub's contracts (D8). Every simulated step carries a "Simulated" label on screen.

What it proves
  • The journey holds together in one account with one approval queue and one results card across four modules.
  • The consent rules shape the flow.
  • The proposal-to-activation path works on a phone-sized screen.
  • Switching one module off leaves the others running.
What it does not prove
  • Demand, price or revenue.
  • Live telephony or real delivery.
  • Entitlement enforcement in the Hub.
  • Approval from a locked iPhone. Real web push runs on localhost desktop only.

The live proof is Phase 1 item A7 on a pilot tenant: the first locked-iPhone approval receipt, with a replay of pause, duplicate event, denial and failed send. The demo moves to the Hub screen by screen as List B lands.
